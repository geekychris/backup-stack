backup-stack

Scheduled backup and cross-location sync for cloud-stack's infrastructure.

Backups

A backup copies one thing, on a schedule, into a destination bucket, as a chain of full and incremental runs you can restore from. Each row says what it copies. One backup per namespace (or per directory) keeps them small, easy to schedule and easy to restore.

What can be backed up
Kubernetes objectsThe manifests of one namespace: ConfigMaps, Secrets, Services, Deployments, StatefulSets, PVCs (the claims), Ingresses, … — enough to recreate the namespace with kubectl apply. Not the files on its volumes or what its databases hold.
Files over SSHEvery file under a directory on a host (wopr's /etc, a photo folder, …), read over SSH with the key in the backup-stack-ssh Secret. Filter rules choose which files.
Volume filesThe files on a PersistentVolume. Coming next. Until then the namespace view shows each volume as not backed up.
Database dumpA consistent dump (pg_dump, mysqldump, mongodump) taken inside the database's own pod. Coming next. Copying a live database's files is not a safe backup; a dump is.

Sync jobs

A sync job keeps a copy of a directory or bucket somewhere else: one-way, newest wins, no history. Use a backup when you need to go back in time; a sync job when you want a mirror (photos to the NAS, a bucket offsite).

What to copy
The Kubernetes cluster to read. spark is the cluster backup-stack runs in; the others are reached with the kubeconfig files in the backup-stack-kubeconfigs Secret (one key per cluster).
One namespace per backup. A namespace that already has a backup says so; you rarely want two.
Leave out
Everything is copied unless you tick it here. Secrets are needed to restore most apps; leave them out only if the destination must not hold passwords (they are stored as Kubernetes keeps them: base64, not encrypted).
What to copy
The machine to read from, by name or IP. It must be reachable from the backup-stack pod on spark.
The account to log in as. Its ~/.ssh/authorized_keys must hold backup-stack's public key, and it must be able to read every file you back up.
An absolute path. Everything under it is copied (except what the filter rules leave out). Symlinks are not followed.
One rule per line, include:pattern or exclude:pattern (or + pattern / - pattern). The first rule that matches a file decides; a file no rule matches is copied. Patterns are relative to the directory: * stays within one folder, ** crosses folders, ? is one character. Examples: exclude:**/node_modules/** · exclude:*.log · only photos: include:**/*.jpg then exclude:**.
SSH keys (advanced)
Leave blank to use /etc/backup-stack/ssh/id_ed25519, mounted from the backup-stack-ssh Secret.
Where the host's key is checked. Add a host with ssh-keyscan host >> known_hosts and update the Secret.
Only for a first test: anyone who can impersonate the host would receive the login.
When and where
Times are in the server's time zone (UTC on spark). The first run is a full copy; later runs copy only what changed. Spread backups out (03:00, 03:15, …) so they don't all run at once. Cron is minute hour day-of-month month day-of-week, e.g. 15 3 * * * = 03:15 daily, 0 */6 * * * = every 6 hours.
The S3 bucket the copies go to. Destinations are set up on the server (BACKUP_STACK_SINKS_JSON or the BACKUP_STACK_S3_* settings); primary is wopr's MinIO.
How it appears in lists and history. Filled in from what you pick; change it if you like.
A disabled backup keeps its settings and history but doesn't run on its schedule.
